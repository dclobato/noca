What the judge can say

On a regular problem the judge runs your code against every test case, compares each output with the expected answer, and reports the most severe outcome it found. They are listed here in exactly that order of severity — the first one to occur anywhere is the one you get, so Accepted is last because it only survives when nothing else happened.

Interactive problems

Some problems have no fixed expected output. Instead the author supplies a program — the custom validator — and the judge runs it beside your solution: everything you print is read by the validator, and everything it prints becomes your input. The two talk until the conversation ends.

Interactive problems still have test cases, and your solution is run against each in turn. A test case holds no expected answer — it holds the data the validator is given before it starts talking to you: the secret number, the hidden graph, the query budget. Each case is a different round of the same game, and your program plays it from the start. The samples on the statement show that data for the rounds the author made public; the rest are hidden, as on any other problem.

Each round ends with the validator deciding how it went — whether your answers were correct, wrong, badly formatted, or over the query or time budget. If a round is accepted the judge moves to the next; the first round you do not pass ends the judgment and becomes your verdict. You are Accepted only when every round passes. The remaining verdicts still come from the judging environment itself, which enforces compilation, memory, output and process limits and detects a crashing program exactly as on regular problems. A crash on your side always wins over whatever the validator was about to report.

On a submission that was not accepted, the submission page shows the conversation from the round that failed, so you can read the exchange exactly as it happened.
