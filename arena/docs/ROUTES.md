# NOCA Arena Routes

> For `url_for()` endpoint names and path parameters, see [URL_FOR_REFERENCE.md](URL_FOR_REFERENCE.md).
>
> **Who may call a route is decided by `arena/dependencies/access_control.py`, not by
> this file.** Arena is default-deny: the app-wide `enforce_arena_authentication`
> gate requires a logged-in session for every path that is not on its public
> allowlist -- exactly `/`, `/dashboard`, `/health`, `/problems`, the root favicon
> assets, and the `/legal/*`, `/help/*`, `/auth/*`, `/assets/medal/*` prefixes -- whatever
> a handler's own dependencies say. A route this document calls *public* or *no login
> required* is therefore one of those paths; everything else needs a session even when
> its description does not repeat it. `tests/arena/test_routes_doc_public_claims.py`
> checks every such claim against the allowlist.

## Static assets

Arena exposes module-specific assets and shared assets through separate named
mounts. Shared images are available at `/static/shared-img/{path}` through the
`static_shared_img` mount. The shared `static_vendor` mount serves circular
Brazilian national and UF flags at
`/static/vendor/img/state-flags/{uppercase-code}.svg`.

## Health (`arena/routes/health.py`)

The health endpoint reports whether Arena's required runtime backends are
available. Public callers are rate-limited before the backend probes run;
trusted local health-check CIDRs bypass this limit.

| Method | URL | Description |
|--------|-----|-------------|
| `GET` | `/health` | Reports PostgreSQL, Valkey, and Arena service health. Returns `200` with `status: "ok"`, `503` with `status: "degraded"`, or `429` when public health probes exceed the configured limit. |

## Auth UI (`arena/routes/auth.py`)

| Method | URL | Description |
|--------|-----|-------------|
| `GET` | `/auth/login` | Arena login page — email/password form with "Remember me" and "Forgot password?". Accepts optional `next`, stores it in a hidden form field, and uses only same-origin path targets. While a Google-first signup is parked to be folded into an existing account (a live `pending_google_existing_uid` session marker), an absent `next` defaults to `/auth/google/link-existing`, so the ordinary post-login chain delivers the user to that confirmation page. |
| `POST` | `/auth/login` | Processes login credentials with auth throttling keyed by ASGI client IP and hashed email. On password-only success records login history as `password` and sets an `arena_access_token` cookie (with `extra_data.tid = get_token_id()`). Every session issues a 1-hour LOGIN JWT stamped with `session_started_at` and is rotated by the middleware at half-life while the user stays active, subject to the optional `NOCA_JWT_REFRESH_MAX_SESSION_SECONDS` cap. Checking "Remember me" additionally sets a 30-day persistent cookie so the session survives a browser restart. Redirects to safe `next` when present, otherwise dashboard. Handles inactive/unconfirmed accounts by re-rendering the login page with a resend-activation button. If login enters 2FA or forced password change, the safe `next` target is preserved in the pending flow token. Lockouts return `429` with `Retry-After`. |
| `POST` | `/auth/resend-activation` | Re-sends the email confirmation link for the account whose ID is stored in the Starlette session by the login handler. Consumes the session key on first use. IP-scoped throttling caps repeated resends; over-limit requests flash a retry message. Its email is charged to the client IP's email budget (`NOCA_EMAIL_BUDGET_USER_MAX`) and handed to the `noca-mailer` worker, the only process that sends mail. |
| `POST` | `/auth/resend-parental-consent` | Re-sends the parental consent email for a pending minor account stored in the Starlette session by the login handler. IP-scoped throttling caps repeated resends; over-limit requests flash a retry message. Its email is charged to the client IP's email budget (`NOCA_EMAIL_BUDGET_USER_MAX`) and handed to the `noca-mailer` worker, the only process that sends mail. |
| `POST` | `/auth/update-parental-email` | Stores or replaces the parent/legal guardian email for a pending account and sends a consent link. Its email is charged to the client IP's email budget (`NOCA_EMAIL_BUDGET_USER_MAX`) and handed to the `noca-mailer` worker, the only process that sends mail. |
| `POST` | `/auth/update-date-of-birth` | Regularises a legacy account missing date of birth before login. Every attempt with a pending session counts against an IP-scoped window (`update_date_of_birth` bucket); over-limit requests get a `429` lockout page with `Retry-After` and perform no write. |
| `GET` | `/auth/change-password` | Render the forced-password-change page. Guards the route by requiring a valid `pending_pw_change_token` in the Starlette session. Redirects to login if the token is absent. |
| `POST` | `/auth/change-password` | Process the forced-password-change form. Validates the `pending_pw_change_token`, enforces password policy, and on success redirects to the pending flow's safe `next` URL or dashboard. The replacement token preserves the original `session_started_at` and `remember_me` metadata, so rotation and the absolute cap continue to apply to the same session. Also serves the voluntary change for a logged-in user. The current-password check is throttled per user id and client IP in the `password_verify` bucket shared with `POST /user/profile/2fa/disable`; a lockout answers `429` with `Retry-After` before any verification, and a correct password resets the counter. Its email is charged to the user's email budget (`NOCA_EMAIL_BUDGET_USER_MAX`) and handed to the `noca-mailer` worker, the only process that sends mail. |
| `GET` | `/auth/2fa` | Arena two-factor authentication page — 6-digit OTP entry. Requires a valid `pending_2fa_token` in the Starlette session. |
| `POST` | `/auth/2fa` | Process the 2FA verification form with auth throttling keyed by ASGI client IP and hashed account email. The account bucket is the real cap here -- reaching this step needs a valid password, so an attacker already holds the credential for the account they are attacking -- and the per-IP bucket therefore locks only once its failures have also spanned `NOCA_AUTH_RATE_LIMIT_2FA_IP_DISTINCT_ACCOUNTS` distinct accounts, the signature that separates spraying from one student fumbling codes behind a school lab's shared NAT address. A successful verification clears only that account's failures; it preserves the IP counter and distinct-account set so a controlled account cannot erase failures sprayed across other accounts. Validates the PENDING_2FA session token, verifies the supplied TOTP or backup code, records completed login history as `2fa` or `backup_code`, and on success issues a LOGIN JWT cookie before redirecting to the pending flow's safe `next` URL or dashboard. The issued LOGIN token preserves the original `session_started_at` and `remember_me` metadata, so rotation and the absolute cap continue to apply to the same session. Lockouts return `429` with `Retry-After`. |
| `GET` | `/auth/signup` | Arena sign-up page — registration form with full name, date of birth, email, password, profile photo, and terms agreement. |
| `POST` | `/auth/signup` | Carries two per-IP fixed windows on the shared `request_rate_limit` primitive, keyed by ASGI client IP over `NOCA_ARENA_SIGNUP_RATE_LIMIT_WINDOW_SECONDS`. A custom `APIRoute` wrapper applies the flood guard (`NOCA_ARENA_SIGNUP_REQUEST_RATE_LIMIT_MAX_REQUESTS`, bucket `arena:signup-requests`, `reason=ip_request_window`) before FastAPI parses form fields or multipart files. The form is then validated, and only a submission that passes validation spends the small attempt budget (`NOCA_ARENA_SIGNUP_RATE_LIMIT_MAX_REQUESTS`, bucket `arena:signup`, `reason=ip_window`), which is counted whatever the outcome from there on and never reset by a successful signup: it pays for the account lookup, the paid IPQualityScore lookups, the insert and the activation email, none of which a mismatched password confirmation or an unchecked terms box reaches. The route then applies the hashed-email auth lockout for already-registered addresses, and optionally accepts a profile photo. A refusal from either window re-renders the form with `429` and `Retry-After`, records an `auth_throttle_lockout` event naming which window it was, and reaches neither the account workflow, the activation email, nor the IPQualityScore lookups. Photo streaming stops at `NOCA_IMAGE_MAX_FILE_SIZE`; browser failures redirect back with a warning. Creates an Arena user account when the email is new, records Terms of Service and Privacy Policy acceptance timestamp, sends activation and parental-consent emails when applicable, and redirects to login with the same success message for new and already registered emails. For an already-registered email it records a `signup_existing_account` security event and sends an out-of-band "you already have an account — log in or reset your password" email to the address owner instead of another activation email, keeping the response indistinguishable from a fresh signup. Lockouts return `429` with `Retry-After`. The activation, parental-consent and existing-account emails are charged to the client IP's email budget (`NOCA_EMAIL_BUDGET_USER_MAX`) and handed to the `noca-mailer` worker, the only process that sends mail. Every new account is also assigned a unique pseudonymous `username`; if the drawn handle is taken between the availability check and the insert, the insert is retried on a fresh draw inside a savepoint. Exhausting those retries re-renders the form with **`409`** rather than the `422` every other validation failure uses — the submission was valid and resubmitting it unchanged is the correct response. |
| `GET` | `/auth/activate` | Validates an email-confirmation JWT and activates the account. Throttled on the shared `token_redeem` bucket (`arena/routes/auth_token_redeem.py`): this `GET` *redeems* the token, so unlike the password-reset link it cannot defer the verdict to a `POST`. The bucket is keyed by the token's **unverified** `sub` claim (falling back to the token itself when there is no payload to read), so every tampering of one user's link accumulates against that user rather than minting a fresh budget per variation. Only a rejected token is counted -- a successful redemption clears that account's counter and a repeat click (`EMAIL_ALREADY_CONFIRMED`) costs nothing, so a mail-client prefetch or a second click cannot lock a working link out. The lock refuses **bad tokens only**: the token is judged first and a genuine link still redeems while its bucket is locked, otherwise anyone who knows an address could hold that account's activation hostage with five garbage tokens. A success never clears the per-IP counter, because the identifier is caller-chosen and the IP bucket is the only cap on guessing. |
| `GET` | `/auth/parental-consent` | Renders the guardian's consent **review page** (child's name and **masked** email, what granting enables, a `POST` form, and a Deny link back to the public dashboard). **Mutates nothing at all** -- no consent change, no events, no mail, and no throttle accounting, because mail scanners and link prefetchers follow links in email and a review page must stay free of side effects. A refused link (missing, malformed, expired, or wrong-action token; unknown account; account in the under-13 blocked band) keeps the pre-existing flash-and-redirect behavior but is **not** counted -- the whole `token_redeem` contract lives on the `POST`. An already-consented account still renders the page, with a note that re-confirming changes nothing. |
| `POST` | `/auth/parental-consent` | Records the guardian's consent from the review form. Re-resolves the token **under a row lock** and grants inside it, so the submit never trusts a validation the `GET` performed and two concurrent submits cannot both transition. Carries the `token_redeem` throttle contract that used to sit on the `GET` (keyed by the unverified `sub`, failures only, genuine link redeems even while locked, IP counter never reset). Refuses an account now in the under-13 blocked band -- a stale link must not restore consent an age change cleared -- while an adult account still redeems, since this link is the only self-service unstick for a holder who turned 18 while consent was pending. Activates the account only when the email-confirmation gate is also satisfied. A real grant bumps `consent_generation`, records `parental_consent_confirmed` and `parental_consent_granted` (plus `account_activated` when it activates), and -- **after** the commit, so the link carries the post-grant epoch -- emails the guardian `parental_consent_confirmed.jinja2`, which is the **only** carrier of their revocation link; a failed delivery of that message is recorded at `warning` severity. A re-submitted form transitions nothing and therefore records no event and sends no mail. Answers **`303`** to the login page. |
| `GET` | `/auth/parental-consent/revoke` | Renders the guardian's revocation confirmation page (child's name and **masked** email, a `POST` form, and a Keep-consent link back to the public dashboard). **Mutates nothing**: mail scanners and link prefetchers follow links in email, so the destructive half is the `POST`. The token must be a valid `PARENTAL_CONSENT_REVOKE` JWT whose `gen` claim equals the account's stored `consent_generation` exactly, on an account whose consent is currently granted and whose holder is still in the 13-17 band (an unknown date of birth refuses). Every refusal -- unknown `sub`, stale epoch, consent not granted, holder now 18, malformed or expired token -- renders one identical page with an identical status, so the link is never an account oracle. |
| `POST` | `/auth/parental-consent/revoke` | Performs the withdrawal. Counts against the IP-scoped `parental_consent_revoke` throttle bucket *before* any database work (`429` + `Retry-After` when locked), then re-resolves the token under `SELECT ... FOR UPDATE` and mutates inside that lock, so two concurrent submissions of the same link cannot both take effect. Clears consent, deactivates the account, bumps `session_version` (killing live JWTs), clears `public_profile` and `full_name_public`, and bumps `consent_generation` -- leaving `ranking_visible` untouched. Records `parental_consent_revoked` and `account_deactivated`, **commits**, and only then emails the guardian and the child separately, each failure isolated so one refusal cannot silence the other or unwind the committed revocation. Answers **`303`** to `/auth/parental-consent/revoked` on success, so a refresh cannot re-submit a token the revocation has already invalidated; only the success path redirects, since a refused submission changes nothing and simply fails again. |
| `GET` | `/auth/parental-consent/revoked` | Static outcome page for a completed withdrawal: what was suspended, that nothing was deleted, and how to ask for erasure. Takes no token and names no account, so the child's identity never travels through a URL, browser history, or a `Referer` header. |
| `GET` | `/auth/password-reset` | Password-reset request page, or new-password form when a reset token is present. The token is deliberately **not** validated here: this route is anonymous and unthrottled, so judging the token would answer "valid, expired, or forged?" for free and without limit, while the `POST` performs the same check behind the `password-reset` throttle keyed on the token. The form renders for any token value and the `POST` stays the single verdict point. |
| `POST` | `/auth/password-reset` | Sends a password-reset email or resets the password for a valid reset token. The request and token-completion paths are auth-throttled and lockouts return `429` with `Retry-After`. The request path keeps the same response copy for existing and unknown accounts. The reset email is charged to the **recipient address's** email budget (`NOCA_EMAIL_BUDGET_USER_MAX`), so N requesters cannot mail one victim, and every send failure -- a spent budget or a provider outage -- answers the same neutral redirect as an unknown address, closing the 200-vs-500 enumeration oracle the route used to have when SMTP was down. |
| `POST` | `/auth/logout` | Revokes the current `arena_access_token` JWT in the Valkey revocation store, deletes the cookie, and redirects to the dashboard with a success flash message. Idempotent: safe to call when no session is active. |
| `GET` | `/auth/accept-terms` | Render the Terms of Service and Privacy Policy acceptance form. Requires a `pending_tos_uid` session key set by the login handler; redirects to login if absent. |
| `POST` | `/auth/accept-terms` | Process the ToS/PP acceptance form. Validates checkbox presence, updates `aceitou_termos_privacidade` and `dta_aceitacao_termos_privacidade` for the pending user, commits, and redirects to login with a success message. Every attempt with a pending session counts against an IP-scoped window (`accept_terms` bucket); over-limit requests get a `429` lockout page with `Retry-After` and perform no write. |

## Google sign-in (`arena/routes/auth_google.py`, `arena/routes/auth_google_complete.py`)

Google is an alternative login door, off by default. When
`NOCA_ARENA_GOOGLE_OAUTH_ENABLED` is false or the client credentials are missing,
every route below answers `404` and the login, signup, and profile pages render no
Google affordance, so a deployment that has not configured an OAuth client is
indistinguishable from one without the feature -- **except** `GET
/auth/google/blocked` (see its row below), which stays reachable on purpose. This
is a whole-feature switch, not a per-account one: a user who linked Google while
the feature was enabled keeps their `arena_user_google_identities` row (and can
still sign in with their Arena password) if the deployment later disables it, but
`/user/profile` no longer offers the Linked Accounts tab and the unlink/avatar-source
routes 404 like everything else here -- the identity can only be managed again once
the feature is re-enabled. The one control that stays available is the
administrator's `POST /admin/users/{user_id}/unlink-google` (see the admin user
rows), so an operator who turned the feature off can still detach the identities
it created.

These paths sit under the already-public `/auth` prefix, so **no authentication is
required** to reach them and each handler gates itself. The OIDC flow itself
(`state`, `nonce`, PKCE with `S256`, and ID-token verification against Google's
rotating JWKS) is owned by Authlib -- PKCE only because the client registration asks
for it, since Authlib leaves it off by default; the redirect URI is derived from `NOCA_ARENA_URL_BASE` (or
the request base URL) rather than configured separately.

| Method | URL | Description |
|--------|-----|-------------|
| `GET` | `/auth/google/login` | Starts the Google sign-in flow. Stores the optional `next` target in the Starlette session beside Authlib's `state`/`nonce`/PKCE verifier — never round-tripped through Google — and redirects to Google's authorization endpoint. Re-validated by `safe_next_url` when the login completes. |
| `GET` | `/auth/google/callback` | Completes a sign-in **or** an account link; the two are told apart by the `pending_google_link_uid` session marker, which the callback consumes only **after** throttle admission and a successful authorization, immediately before dispatch — never on entry. A callback refused with `429` has not reached Authlib, so its `state` and code are still valid and the user will retry them; consuming the marker first would make that retry look like an ordinary login and, for an unknown subject, create a stray second account (for a logged-out and a still-authenticated linker alike, since the current-user check below only runs once the callback knows it is a link). A forged callback that fails the state check likewise spends nothing. A link is additionally verified against the request's **current authenticated user**: the marker names an account, and unless the request is still authenticated as exactly that account the link is refused with the generic failure message (nothing linked, no account created). The marker deliberately survives logout — it is what makes a logged-out callback recognizable as a link and therefore refusable, rather than falling through to the signup path and creating a stray account. Anonymous and publicly reachable, so it is auth-throttled per client IP (`google-login` action) ahead of everything else; lockouts return `429` with `Retry-After`. Refuses an unverified Google email, a rejected token exchange, and a missing subject claim with one generic message and a `google_login_failure` event. A known `google_sub` runs the same `evaluate_account_access_gates` the password path runs, records login history as `google`, and hands off to the shared `complete_arena_login` (terms gate, 2FA gate, forced-password-change gate). An unknown `google_sub` creates an inactive account and redirects to the completion step. A Google address matching an existing Arena account is **not** auto-linked. |
| `POST` | `/auth/google/link` | Requires a logged-in Arena user. Marks the session with the account to link and redirects to Google. Because linking only ever starts from an authenticated session, the Google address need not match the Arena address. |
| `POST` | `/auth/google/unlink` | Requires a logged-in Arena user. Refused by the last-method guard when the account has no usable password (`password_is_placeholder`), since unlinking would leave no way in; setting a password through the ordinary reset flow lifts the refusal. Deletes the identity row and its cached Google avatar, reverts avatar selection to the preserved Arena photo/fallback, records `google_account_unlinked` at warning severity, and emails the user. |
| `POST` | `/auth/google/avatar-source` | Requires a logged-in Arena user with a linked Google identity. Form `source` is `arena` or `google`. Selecting Google downloads, validates, resizes, and locally caches the current Google picture before changing the preference; a download failure leaves the prior source and cache intact. Selecting Arena preserves the Google cache but serves the user's uploaded Arena photo or fallback. |
| `GET` | `/auth/google/complete` | Renders the step that collects the date of birth and terms acceptance Google cannot supply. Requires a `pending_google_signup_uid` session key set by the callback; redirects to login if absent. Shows which Google account authorized the signup. |
| `POST` | `/auth/google/complete` | Applies the same LGPD age rules as the ordinary signup: under 13 redirects to `arena_google_blocked` and the account stays inactive; 13–17 stores the guardian address, keeps the account inactive, sends the existing parental-consent email, and redirects to `arena_google_pending_consent`; an adult is activated, records login history as `google`, and is logged straight in. Terms acceptance is required. |
| `GET` | `/auth/google/blocked` | Explains the under-13 refusal. Stateless: reads no account and no session, so it can be reloaded or reached again on a later visit while the account stays inactive. Unlike every other route in this table, it stays reachable (`200`) even while `NOCA_ARENA_GOOGLE_OAUTH_ENABLED` is off: a visitor already refused here must keep being able to see why, so disabling the feature later cannot turn their bookmark into a dead link. |
| `GET` | `/auth/google/pending-consent` | Renders the guardian-consent chronology for a held 13-17 Google signup: when the account was created, that a guardian was emailed at the stored address, and the date consent stops being required. Requires a `pending_google_consent_uid` session key, read rather than consumed so the page survives a reload and a resend. If the account has since become active (a guardian consented through the unrelated emailed-link flow), redirects to login instead of restating stale copy. |
| `POST` | `/auth/google/pending-consent/resend` | Re-sends the parental-consent email for a held Google signup, IP-throttled under a `resend_google_parental_consent` action distinct from the password-signup resend so the two flows cannot exhaust each other's budget. Always redirects back to the waiting page, never to login, so the flash augments a page that already states the account's status rather than a bare form. |
| `POST` | `/auth/google/complete/existing-account` | The "I already have an account" exit from the completion form (`auth_google_existing.py`). Requires the `pending_google_signup_uid` marker and a never-completed (`needs_completion`) Google-first account; swaps that marker for `pending_google_existing_uid` (time-stamped, 30-minute lifetime) and redirects to the password login. Writes nothing: the orphan stays exactly as the callback left it until the confirmation below decides its fate, so abandoning here changes nothing. |
| `GET` | `/auth/google/link-existing` | Requires a logged-in Arena user and a live `pending_google_existing_uid` marker naming an orphan that is still `needs_completion` and still holds its identity; otherwise clears the marker and redirects to the profile's Linked Accounts tab with a warning. Renders a confirmation that names the Google address and the signed-in account. Reached through the login's `next`, so the whole ordinary chain — terms, 2FA, forced password change — has already run before anything can be linked; no `GET` mutates. |
| `POST` | `/auth/google/link-existing` | Form `decision`. `link` re-creates the orphan's Google identity under the signed-in account and deletes the orphan row in one transaction (`google_signup_service.transfer_pending_signup_identity`), records `google_account_linked` (`source=existing_account`) and a warning-severity `google_signup_discarded` naming the discarded id, emails the user, clears the marker, and redirects to Linked Accounts. A signed-in account that already has a Google identity is a stated conflict (`google_link_conflict`, `source=existing_account`): the savepoint rolls the deletion back with the failed insert, so nothing is deleted. Any other `decision` clears the marker and changes nothing, so the Google door can still finish that signup as a separate account later. |

An account resuming through `/auth/google/callback` after leaving the flow mid-way
lands on whichever of `arena_google_complete`, `arena_google_pending_consent`, or
`arena_google_blocked` matches its current state, rather than the generic
account-deactivated message: `google_signup_service.describe_pending_google_signup`
discriminates an in-flight Google-first signup from an ordinary account an
administrator deactivated by checking `password_is_placeholder`, which only a
Google-first signup ever sets.

A Google-first signup whose Google address differs from the user's existing Arena
address is indistinguishable, at the callback, from a genuine new user, so it creates
an account that holds the Google subject and the real account can never link it from
its profile (the subject's `UNIQUE` constraint refuses it). The completion form's
"Already have an Arena account under another email?" exit is the self-service way
out, resolved through the three `link-existing` rows above; the administrator's
`POST /admin/users/{user_id}/unlink-google` is the support escape once such a signup
has been *completed* by mistake.

## Announcements (`arena/routes/announcements.py`)

The platform announcement board (#138). Rows live in the shared `announcements`
table and are scoped by `domain`; these routes serve `domain=arena` only, so a Web
announcement answers the same `404` an unknown id does. Both paths are on the
public allowlist (`/announcements` prefix in `arena/dependencies/access_control.py`),
and the sidebar carries an "Announcements" entry for everyone. Only `GET` is
registered: a published announcement is immutable.

| Method | URL | Description |
|--------|-----|-------------|
| `GET` | `/announcements` | Paginated list of Arena announcements, newest first, fixed at 25 per page (`?page=`, clamped). Each title links to its detail page carrying the current page; each row is `id="announcement-<id>"` with `noca-target-row`, so a return with that fragment keeps the row highlighted. No authentication required. |
| `GET` | `/announcements/{announcement_id}` | One announcement: title, publisher label, publication time, and the Markdown body rendered in the browser through the single shared pipeline (KaTeX, Mermaid, external links). `?page=` (default 1) is the list page the reader came from; the Back button returns to `/announcements?page=<N>#announcement-<id>`. `404` when absent or published on Web. No authentication required. |
| `POST` | `/announcements/{announcement_id}/acknowledge` | Records that the **logged-in** user acknowledged a *required* Arena announcement (form field `acknowledge`, the pop-up's checkbox; `400` when missing). Requires the user itself (`require_arena_user` → `401`), since the public prefix keeps the global gate from doing so. Idempotent: an acknowledgment already on file still answers success. `404` for an unknown id, a Web announcement, or one that is not required. Commits and redirects (`303`) to the same-origin `Referer` (the page the pop-up was on), falling back to the dashboard. |

**Mandatory announcements.** An announcement published with `required` pops up for every logged-in user on every page they load until they acknowledge it. The lookup is the app-level dependency `load_pending_required_announcement` (`arena/dependencies/required_announcements.py`), which runs only for authenticated HTML `GET` page loads outside `/auth` (not JSON polls, SSE, heartbeats, HTMX fragments or `POST` re-renders) and leaves the oldest pending announcement, with the pending count, on `request.state`; `_base.html` then includes `_partials/_announcement_required_modal.html`: a static-backdrop modal with the Markdown body, a "1 of N" counter when several are queued, and an Acknowledge button enabled by the checkbox. Acknowledging reloads the page, which shows the next one.

## Per-user read ceiling

Every `GET` route on Arena's polled and authenticated-read routers --
notifications, problem browsing (`problems`, `problem_editorial`), the public
profile, ranking, submissions, and the `/admin` user routers -- plus
`GET /live`, `GET /live/feed.json`, `GET /user/submissions/status.json`, and
the two timer-driven presence `POST` endpoints carries a
**loose per-user ceiling** (`arena/dependencies/user_read_rate_limit.py`, bucket
`arena:user-read`, knobs `NOCA_ARENA_USER_READ_RATE_LIMIT_*`, default 300 per
user per minute). It is attached to the *router* wherever the whole surface
qualifies, so a `GET` partial added later inherits it, and per route where the
router also carries an SSE stream. State-changing requests ignore the read
ceiling; the presence endpoints opt in because they are machine-driven polls.

Each of these calls costs a bounded amount and legitimate clients poll them
every few seconds, so the budget sits roughly an order of magnitude above the
fastest honest poller. The key is the account id read from
`request.state.validated_token` (already populated by `ArenaAuthMiddleware`, so
the dependency does no I/O of its own), falling back to the client IP for an
anonymous caller -- which is what gives the public routers here a ceiling
without one shared address spending an account's. Over budget the answer is
`429` with `Retry-After`, and `shared/static/js/htmx-poll-backoff.js` parks the
page's *timer-driven* partials for that long; user-initiated requests are never
cancelled.

The two SSE streams are deliberately outside it: an open stream is one
connection held for minutes, bounded by
`arena/dependencies/sse_limits.py` instead.

## Per-user problem-download budget

Two routes on the problems router build an artifact rather than render a page:
`GET /problems/{n}/export` and `GET /problems/{n}/sample-testcases.zip`. The read
ceiling above is sized for polled partials whose cost is bounded; a package build is
not, so both carry a second, much tighter **per-user budget**
(`arena/dependencies/problem_export_rate_limit.py`, bucket `arena:problem-export`, knobs
`NOCA_ARENA_PROBLEM_EXPORT_RATE_LIMIT_*`, default 10 per 10 min), stacked under the
ceiling and refusing with `429` + `Retry-After`. It is charged **before** the cache is
consulted, so a hit and a miss cost the same budget and editing a problem cannot widen
it. Both artifacts are served from the on-disk cache under
`NOCA_ARENA_PUBLIC_PROBLEM_PACK_PATH`, keyed on `arena_problems.public_export_generation`
-- the port of Web's #152 fix (#204).

## Per-user export and report budgets

Six more routes build something per request rather than render a bounded page,
and each carries a tight **per-user budget** of its own
(`arena/dependencies/export_rate_limit.py`, #157), one bucket per surface so a
teacher paging through reports never spends an administrator's export
allowance. `arena:admin-export` (`NOCA_ARENA_ADMIN_EXPORT_RATE_LIMIT_*`, default
20 per 10 min) covers the two administrative downloads,
`GET /admin/problems/{id}/export` and `GET /admin/dashboard/security-events.csv`;
`arena:teacher-report` (`NOCA_ARENA_TEACHER_REPORT_RATE_LIMIT_*`, 60 per 10 min)
covers the class-wide report page and its CSV, the per-set report, and the
per-student drill-down under `/classes/{id}/problem-sets/`. Both are route-level,
refuse with `429` + `Retry-After`, key on the same validated account id the
read ceiling uses (`arena_user_key`), and are charged before the handler runs,
so a request the route's own guard then refuses -- an unknown problem, a class
the caller does not teach -- still spends one.

Enabling is refused (redirect to the edit page with a flash) unless the problem can actually judge, per the shared judgeability contract read from its **stored strategy**: a standard problem needs at least one case with an expected output on every case; an interactive one needs an active `VALID` validator and at least one secret case; the reserved output checker can never be enabled. |
| `POST` | `/admin/problems/{problem_id}/set-enabled` | Set the problem's publication state from the judgment-data editor, whose header carries the same **Save and enable** / **Save and disable** submitters the definition editor does. `save_action` names the *target* state (`enable` / `disable`) rather than toggling, so a double submit is idempotent, and `next_url` (same-origin path only) returns the author to the judgment page they acted from. Enabling applies the same judgeability gate `toggle-enabled` does, refusing with a flash on the same page. |
| `POST` | `/admin/problems/{problem_id}/delete` | Permanently delete the problem and all dependent data (test cases, submissions, judgments, AI reviews, solve/attempt/favourite records). Requires current-password confirmation, checked on the shared verification throttle (`arena/routes/auth_throttle.py`, `password_verify` bucket): a wrong password is counted and recorded, and past the cap the `429` throttled page answers before the password is read, so a locked actor deletes nothing even with the right password. Redirects to the problem list on success or back to the edit page on wrong password. |
| `POST` | `/admin/problems/{problem_id}/rejudge-all` | Create new `QUEUED` judgment rows for every *settled* submission of the problem and enqueue them on the low-priority autojudge queue (`judge:queue:pending`). Requires current-password confirmation, checked on the shared verification throttle (`arena/routes/auth_throttle.py`, `password_verify` bucket): a wrong password is counted and recorded, and past the cap the `429` throttled page answers before the password is read. Then a per-problem **cooldown** (`NOCA_ARENA_REJUDGE_COOLDOWN_SECONDS`, `shared/services/rejudge_cooldown.py`) refuses a repeat with a danger flash naming the wait. Submissions whose current judgment is still `QUEUED`/`DISPATCHED`/`JUDGING` are skipped rather than superseded and counted in the flash, so a repeat click queues nothing new; the selection runs under `FOR UPDATE` on the submission rows. An accepted action writes one warning-severity `admin_action` security event (`rejudge_all`, with the queued and skipped counts) in the same transaction as the judgments; queuing nothing releases the cooldown. An optional safe local `next_url` returns the author to the judgment-data page that requested the action; a missing or unsafe value returns to the definition editor. |

## Arena Admin – Judgment data (`arena/routes/admin_problem_judgment.py`)

Test cases, the custom validator and the sample interactions are edited on their
own **pages**, reached from the problem list's *Judgment data* action, because a
problem can hold many large test cases and carrying them inside the form that
edits its statement is what made that form unwieldy. Every action applies
immediately through the staged swap; only the rows an author types inline wait for
that page's own Save, since typed text is the only state the browser holds that the
server has not seen. A standard problem is offered the test-cases page alone.
Every page starts with one judgeability summary: it names missing cases or an
unavailable validator, distinguishes validator compilation from readiness, and
offers the password-confirmed **Rejudge all** action when Arena submissions
already exist. Test-case rows keep **Edit** visible and place download,
replacement, sample visibility, and removal under a labeled **More** menu.

Ownership is enforced by a FastAPI dependency rather than a call, so a route that
omits it fails to resolve rather than silently letting an editor touch another
owner's problem. A problem the caller may not edit answers **404**, not 403, like
every other Arena admin problem route: telling a stranger that a problem exists is
itself a leak.

## Ranking (`arena/routes/ranking.py`)

Login required: every ranking route takes `require_arena_user`, and none of the paths is on the public allowlist.

| Method | URL | Description |
|--------|-----|-------------|
| `GET` | `/ranking` | Ranking landing page with two choice cards: User Ranking and Affiliation Ranking. |
| `GET` | `/ranking/users` | Paginated user ranking (50/page). Query params: `search`, `page`. Every participant is displayed under their pseudonymous `username` unless they are an adult who opted in to `full_name_public`; the masked-email column is omitted entirely for an age-shielded user. `search` runs the **age-shielded** candidate query in `identity_search_service` (`prepare_public_user_search`): PostgreSQL full-text plus substring and 3+-character fuzzy matching on the name **for users who are not age-shielded**, substring and fuzzy matching on the username for everyone, and substring-only matching on the email (an address is an exact identifier). A shielded user is therefore findable by their handle but never by their real name — answering that question would reconstruct the very secret the pseudonym hides. Websearch operators apply — `"quoted phrase"`, `a OR b`, and `-term` keep only the full-text branch — while typed `%` and `_` are matched literally. Search only filters: global rank is computed via SQL `RANK()` over all eligible users before it is applied, so rank positions stay globally consistent and never renumber. |
| `GET` | `/ranking/affiliations` | Paginated affiliation ranking (50/page). Query params: `search`, `country_code`, `subdivision_code`, `page`. `search` matches the affiliation name with the same full-text, substring, and fuzzy branches and the same operator semantics, and likewise only filters without reordering. Country/subdivision filter options are sourced from actual affiliation data, not the full pycountry list. |

## Custom validator routes (`arena/routes/admin_problem_validator.py`)

The validator is staged from the judgment-data **validator page**, which posts to
the upload endpoint below and applies it immediately; every one of these routes
returns to that page, since that is where a refusal has to be corrected and where
the compile status polls. The status endpoint supports HTMX polling while
compilation remains pending.

- `POST /admin/problems/{problem_id}/validator` stages and enqueues a candidate.
  Replacing a configured validator means removing it first.
- `GET /admin/problems/{problem_id}/validator/status` renders current status.
- `GET /admin/problems/{problem_id}/validator/source` downloads the current
  source (active revision, falling back to a staged candidate).
- `GET /admin/problems/{problem_id}/validator/source/view` renders the current
  source with syntax highlighting and line numbers.
- `POST /admin/problems/{problem_id}/validator/remove` clears both revisions. It
  requires a `keep_interactions` form field whose value is exactly `"true"` or
  `"false"` — the edit page posts it from a confirmation modal. `"true"` hides the
  problem's sample interactions (they resurface if a validator is added again);
  `"false"` deletes them permanently. The field is a strict string rather than a
  `bool` on purpose: FastAPI would coerce `1`, `on` and `yes` too, and the choice
  between hiding data and destroying it must not hinge on a spelling. Any other
  value, or none, is a 422.
  Removal never changes the problem's validation strategy: it stays interactive
  and simply stops being judgeable until a replacement validator compiles.

### Sample interactions

An interactive problem has no public test cases. Its public examples are **sample
interactions** — up to five author-written transcripts of the conversation a
correct program has with the validator, rendered on the problem page with the same
transcript UI that shows a submission's recorded attempts.

- `GET|POST /admin/problems/{problem_id}/interactions/{si_id}/edit` view and save
  one interaction.
- `POST /admin/problems/{problem_id}/interactions/{si_id}/move` reorders one
  interaction (`new_ordinal` query param) and returns the refreshed list partial
  for the drag-and-drop handler.

Deletion and reordering apply immediately, exactly like test cases. Only the
transcripts an author types inline (`si_transcript_N` / `si_explanation_N`
add-rows) wait, and they are applied by the interactions page's own Save.

A problem with a configured validator must have **zero public test cases and at
least one secret one**. Staging a validator demotes any existing public case to
secret, the sample toggle is refused while a validator is configured, and no edit
path may remove the last secret case. Arena problem creation may still stage a
validator on a brand-new *disabled* draft with no test cases at all; that draft is
only forced to be complete at `toggle-enabled` and at submission time.
